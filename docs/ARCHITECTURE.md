# DraftPay Architecture

Status: focused Arc Testnet MVP
Last updated: 2026-07-21

## System shape

```text
Browser (Next.js + wagmi)
  |-- reads Arc directly with viem
  |-- asks the client wallet to create/fund/select/settle
  |-- calls bounded server routes for specification, verification, and agent runs
  |
  +--> DraftPayContestFactory --> one DraftPayContest per brief --> Arc Testnet USDC
  |
  +--> Builder Agent --> x402 buyer --> Circle Gateway / paid brief-analysis service
  |
  +--> local JSONL evidence + content-addressed artifact files
```

There is deliberately no custom blockchain indexer or database. Contract state and receipts are read directly from Arc. Local JSONL/artifact persistence exists only for public demo evidence and generated bytes; it never authorizes settlement.

## Packages

- `apps/web`: Next.js App Router UI and thin server routes.
- `apps/agent`: decision engine, model adapter, static artifact preparation, hashing, x402 buyer, proof, and evaluator writes.
- `apps/x402-service`: Express service exposing paid brief analysis.
- `packages/contracts`: Foundry contracts, tests, and deployment script.
- `packages/chain`: Arc constants, ABIs, explorer helpers, and receipt checks.
- `packages/shared`: schemas, exact-USDC helpers, fixtures, and domain types.
- `packages/ui`: reusable UI primitives.

## Onchain design

`DraftPayContestFactory` stores the verified USDC address and creates an independent `DraftPayContest` for each approved brief. The client approves and deposits the exact prize. The factory has no privileged settlement role.

Submissions commit a deliverable hash and bounded metadata URI. Duplicate hashes are rejected. The evaluator may qualify and rank at most three submissions. All terminal loops operate over that bounded set.

```text
Created --fund--> SubmissionOpen --deadline--> Evaluation --rank--> AwaitingSelection
       `--cancel--> Cancelled                               |--select--> SettledWithWinner
                                                          |--reject/expiry--> SettledWithoutWinner
                                                          `--zero qualified--> Refunded
```

DraftPay follows ERC-8183's create/fund/submit/evaluate/complete sequence and content-hash delivery semantics, but it does not claim compliance. Multi-builder competition, bounded ranking, client selection, and the no-winner pool are DraftPay-specific.

### Trust and invariants

- The evaluator can qualify/reject/rank but cannot choose a winner, change the prize, withdraw, or select arbitrary payout recipients.
- Winner settlement pays exactly the original prize: 95% to the selected winner and the 5% remainder across other finalists; if none exist, the winner receives all.
- No-winner settlement pays 15% / 10% / 5% by available rank and refunds every unused amount.
- No-qualified settlement refunds the entire prize.
- Effects and terminal state are recorded before transfers; funding and settlement use a reentrancy guard.
- The unaudited MVP has no bond, dispute, governance, upgrade, or mainnet claim.

## Agent path

The client approves a Zod-validated specification before funding. For a real run, the Builder Agent reads the pinned contest's token, state, prize, deadlines, qualification count, and specification hash directly from Arc. It refuses local metadata whose canonical hash or economic terms do not match.

The decision engine considers supported category, state, lead time, estimated generation/verification/x402 costs, qualification probability, expected reward, tools, request/session/daily budgets, allowlisted origin, and emergency pause. A user explicitly triggers one run; continuous discovery is stretch scope.

The default model adapter uses a prepared safe static artifact. A provider adapter is available when configured. Verification parses static HTML and enforces required sections/text, native CTA and form controls, accessibility baseline, responsive CSS constraints, prohibited scripts, and duplicate hashes. Hard failures cannot be overridden by an AI rubric. Submitted repositories are never installed or executed.

Real artifact bytes are stored by content hash and served with sandboxing. The proof URI must use a configured public `AGENT_ARTIFACT_BASE_URL`. The evaluator command separately writes hard-check evidence and the bounded ranking.

## x402 and spending safety

The seller uses Circle's `@circle-fin/x402-batching` middleware when real seller configuration exists. The buyer receives 402 requirements, validates origin and price, authorizes with a server-only EOA, retries, and accepts only a paid response. Fixture mode is structurally separate: it quotes the seller's advertised price so the decision is genuinely priced, and always records `paymentOccurred: false` with `amountAtomic: "0"`.

Controls include per-request, per-session, and per-day atomic limits, an origin allowlist, emergency pause, process-local concurrency lock, and web rate limit. Privileged web runs additionally require an operator-entered bearer token; the wallet private key never enters the browser.

## Evidence boundary

Public, non-secret decisions, payment facts, and confirmed proof receipts append to `.demo/evidence.jsonl`. Exact artifact bytes live under `.demo/artifacts`. Generated output truthfully says `not-captured` unless a screenshot exists.

The UI labels evidence real only after a successful Arc receipt or settled Circle payment is verified. Explorer URLs are derived from validated hashes and addresses, never fixtures. Winner source release uses a one-time wallet signature bound to the client, contest, receipt, and selected artifact, followed by direct receipt/client checks.

Real deployment still requires funded Testnet wallets, Circle configuration, and a hosting login. No address, payment ID, receipt, or public URL is recorded before success.
